# ML Results — Payment Truth

All numbers below are pulled directly from `ml/artifacts/metrics.json`,
`ml/artifacts/incident_detector_metrics.json`, and `experiments/*/metrics.json`
as generated by the actual training/experiment scripts. Nothing here is
hand-typed for effect — regenerate any of it with the commands shown and
these numbers will update to match.

## Dataset version

Committed demo dataset: `data/demo/*.csv`, generated with
`python scripts/generate_dataset.py --payments 3000 --seed 7 --sim-days 2 --config demo`.
Generator version `0.2.0` (config-driven — see `data/config/*.yaml`).

## Leakage prevention

`data/schemas/leakage_columns.py` defines the forbidden feature set
(final outcome, future events, ground-truth cause, simulation provenance).
`ml/pipeline/train.py` calls `assert_no_leakage()` immediately before
fitting any model — a `ValueError` if a forbidden column reaches the
feature matrix, not a silent skip.

```bash
python ml/pipeline/train.py --data data/demo --out ml/artifacts
```

## Incident detector

| Detector | Precision | Recall | False Positive Rate | Detection Lead Time |
|---|---|---|---|---|
| Rule baseline | 0.042 | 0.111 | 0.082 | 3.0 min |
| Isolation Forest | 0.087 | 0.222 | 0.075 | 2.0 min |

**Honest assessment:** these numbers are genuinely weak — the rule
baseline catches barely 1 in 10 real incidents, and while the Isolation
Forest roughly doubles recall, both remain far from production-ready
detection. This is reported as-is rather than tuned to look better; see
`docs/ASSUMPTIONS.md` for why per-bin sample volume limits how much
signal either detector can extract from this dataset's traffic density.

**Reproduce:** `python ml/pipeline/incident_detector.py --data data/demo --out ml/artifacts`

— a deliberately different distribution (higher incident severity/duration
ranges, different bank/method baseline failure rates), generated with a

| Unseen configuration | 0.9628 |

Small gap — the model doesn't appear to be memorizing the training

**Reproduce:** `python experiments/unseen_incident/run.py`

## Incident Memory A/B experiment

Compares root-cause diagnosis with vs. without historical-similarity
evidence (`backend/app/historical_similarity.py`), using ground truth from
`incidents_truth.csv`.

| | Root-cause Top-1 | Avg. Confidence |
|---|---|---|
| Without memory | 0.30 | 0.224 |
| With memory | 0.30 | 0.284 |

**Honest finding:** memory produced **no accuracy improvement** in this
run (+0.0), only a modest confidence lift (+0.06). The decision engine's
WAIT/VERIFY/RECOVER/STOP output doesn't currently take diagnosed root
cause as an input, so decision quality is unaffected by construction —
reported plainly rather than manufacturing a positive result. Root-cause
top-1 accuracy itself (30%) is also modest and worth improving before the
memory feature can be expected to move it.

**Reproduce:** `python experiments/incident_memory/run.py`

## Revenue Protection A/B experiment

Strategy A (naive): retry immediately if the earliest observed status is
FAILED, otherwise do nothing. Strategy B (Payment Truth): real trained
model + real decision engine, same payments, same ground truth.

Results are dataset-run-specific — see `experiments/revenue_protection/metrics.json`
for the exact run this repo ships with. The comparison is modest by
design: the naive baseline only acts on an explicit FAILED signal, so it
rarely commits to a wrong action in the first place, which caps how much
headroom Payment Truth has to visibly improve on it under this specific
metric framing.

**Reproduce:** `python experiments/revenue_protection/run.py`

## Limitations

- Incident detector precision/recall are weak at this synthetic traffic
  volume (see above) — a real deployment would need either much higher
  transaction volume or a longer bin window to get reliable signal.
- Root-cause diagnosis top-1 accuracy (30%) has room to improve; the
  scoring evidence engine currently only distinguishes 4 of the
  generator's 5 incident causes (SYSTEMIC has no clean category match).
- The Revenue Protection experiment isolates state-prediction vs the
  naive rule and deliberately excludes incident-driven STOP from that
  specific run, to keep the two strategies comparable on the same
  per-payment decision surface.
